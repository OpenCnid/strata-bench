# M1.1b native key input implementation

M1.1b is now in_progress. A bounded input engine and its native callback/polling
adapter are implemented, but authentic effects and the settings adapter are still
unverified. T05/G1 remain not_run. This is a dependency of the full repair cycle,
not a completed cycle or a newly advertised gameplay capability.

## Consumer and route

Read-only inspection of the installed Curios 1.19.2-5.1.6.4 artifact (SHA256
`1f7742d6c4f6b6cd8d106e54181255c2d264194ba232d42901ef90da6b91e635`)
confirms `ClientEventHandler.onKeyInput` runs at END client tick, consumes
`KeyRegistry.openCurios`, requires `Minecraft.isWindowActive`, and sends its own
open-screen packet. Exact bytecode and mapping evidence are retained privately.
The implementation never invokes that handler or sends that mod packet itself.

`NativeKeyInput` calls Minecraft's ordinary `KeyboardHandler.keyPress` with the
current window, a GLFW-derived scancode, press/release and modifier flags.
`KeyPollingMixin` targets the pinned 1.19.2 `InputConstants.isKeyDown` callsite
(`m_84830_(JI)Z`). Its override exists only for the owned session's window and
client thread; other windows/threads and inactive sessions retain native polling.
Modifier state changes before each callback; release uses reverse order.
Admission probes the actual transformed polling path before any key event and
refuses a missing hook. This check is implemented, not authentically exercised.

The declared candidate policy is `native-window-key-callback-polling/1`.
It is software input in the native client, not evidence of physical OS delivery.
Raw GLFW/custom polling consumers are not covered by the InputConstants hook.
No key becomes a tested pool member from its constant, encoding or scancode.
The final profile still needs consumer qualification, actual effects and the
complete GUI/game/chat matrix; unknown consumers remain conservative conflicts.

## Safety and integration

`KeyInputSession` implements the existing motor interface. It accepts only a
bounded single key or single Shift/Control/Alt chord from the supplied candidate
pool, with a 1–2,000ms requested hold. Ordinary and reserved safety emitters are
separate. Presses, waits, release callbacks and logical cleanup pass through their
emitters. A journal failure cannot suppress safety release; it remains an error,
and an ambiguously delivered callback is never replayed.

The native adapter pins the client thread, window, player, level and connection;
it requires actual window activity and no loading overlay. An independent client
tick listener releases on context loss or an over-limit/invalid monotonic clock.
Tick scheduling and a stalled client still require the external worker guardian;
these synthetic checks do not prove a real wall-clock release bound.

Cancellation remains a failure, not successful gesture completion. Cleanup
attempts all owned releases, clears logical keys/queued clicks and sampled player
inputs, and ends held use/digging without resetting physical momentum. Both
existing game/settings release paths and shutdown call the session stop hook.
The mixin and listener are inert without a session. The ordinary ActionBatch
parser still rejects input mode, and the title-only settings bridge is unchanged.

No caller currently admits an input session into a settings verification run.
Next connect this engine to the transaction-owned, budgeted verification lane
and passive intended/competing effect observations. Preserve exclusive ownership,
revision/body checks and authenticated source identity. Then exercise the actual
Curios/competing controls and restart/rollback cycle on the isolated exact profile.
Do not expose this through a second unfenced input writer or promote a bare
successful callback to an effect pass.
